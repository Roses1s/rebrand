# Код-ревью макета CRM Детроид

**Дата:** 06.11.2026. **Ветка:** `arena/53b90abe-rebrand`, коммит `dc347a3`.
**Объём:** 8 492 строки в `src` (33 файла), почти 4 000 из них — CSS.

Что смотрел: хранилище и данные, оболочка и настройки, воронка (канбан, список,
перетаскивание), карточка лида, клиенты, заявки, задачи, аналитика, админка,
UI-компоненты, токены и стили, конфигурация сборки. Проверял чтением кода,
сборкой (`npm run build` — зелёная, 441 КБ) и серверным рендером всех маршрутов.
Браузера в песочнице нет, поэтому жесты, контраст и поведение при реальном
перетаскивании не проверял — только по коду.

и недоделки, каждая правится в одном-двух файлах.

## P1. Существенное

### 1. Удалённые лиды возвращаются после перезагрузки
`src/app/store.jsx`, функция `load()`:

```js
return Array.isArray(parsed) && parsed.length ? parsed : fallback;
```

Если пользователь удалил все лиды (или выделил все и нажал «Удалить»), в
хранилище лежит пустой массив, а `load` считает его «нет данных» и подставляет
демо-набор. После F5 доска снова полная. Пустой массив — это valid состояние,
его нельзя путать с отсутствием ключа.

**Как чинить:** проверять только `Array.isArray(parsed)`, а fallback отдавать
лишь когда ключа нет или JSON битый.

### 2. Акцент и плотность не восстанавливаются при открытии страницы
`data-accent` и `data-density` выставляются только в `SettingsPage`. На любой
другой странице (и после перезагрузки `/crm`) применён только `data-theme`.
Итог: выбрал изумрудный акцент, перешёл в воронку — снова индиго; в настройки
зашёл — опять изумрудный.

**Как чинить:** один модуль вида `applyPreferences()` (тема + акцент +
плотность), вызывать его в `main.jsx` до рендера и при изменении настроек.

### 3. Тема живёт в двух независимых состояниях
`Shell` держит `useStored("crm.theme")`, `SettingsPage` — свой
`useState(readStored("crm.theme"))`. На странице настроек `Shell` уже смонтирован,
поэтому после переключения темы в карточке «Оформление» иконка в шапке остаётся
прежней, а клик по ней переключает от устаревшего значения — визуально «не туда».

**Как чинить:** вынести тему в контекст (или подписку на `storage`), чтобы
источник правды был один.

### 4. KPI «Без движения» считает задачи, а не лиды
`src/pages/FunnelPage.jsx`:

```js
const overdueTasks = TASKS.filter(...).length;   // задачи
...
{ label: "Без движения", value: String(overdueTasks), foot: "лидов ждут звонка" }
```

Карточка про лиды показывает число просроченных задач из статики. Создание
задачи в «Задачах» на неё не влияет, а лид с флагом `late` не учитывается.

**Как чинить:** считать `myLeads.filter((lead) => lead.late).length`.

### 5. «Потенциальные» привязаны к индексу этапа
`const potentialStage = stages[3]`. Переименовали, переставили или удалили
этапы — цифра начинает означать чужой этап. Аналитика делает то же самое через
`stageId === 4`.

**Как чинить:** у этапа должен быть признак (`isPotential`/`kind`), а не позиция.

### 6. При включённом фильтре карточка падает не туда
`resolveTarget` считает индекс среди **всех** лидов этапа, линия вставки
рисуется по **видимым**, а `moveLead` применяет индекс к полному списку:

```js
dropIndex = order.slice(0, dropTarget.index).filter(visible).length; // линия
moveLead(lead.id, target.stageId, target.index);                     // вставка
```

С включёнными «Горячими» карточка встаёт между невидимыми соседями — после
снятия фильтра оказывается не там, где её отпустили.

**Как чинить:** передавать в `moveLead` позицию соседа («перед каким лидом
вставить»), а не числовой индекс в отфильтрованном списке.

### 7. Карточка лида показывает этап предыдущего лида и «воскрешает» удалённые
`src/pages/LeadPage.jsx`:

```js
const [stageId, setStageId] = useState(lead?.stageId ?? 1);
const lead = leads.find(...) ?? ALL_LEADS.find(...);
```

- При переходе с лида на лид компонент не перемонтируется, `stageId` остаётся
  от предыдущей карточки — в шапке подсвечен не тот этап.
- Если лид удалён с доски, он всё равно находится в `ALL_LEADS` (демо-данные) —
  ссылка открывает «удалённую» запись, а переключение этапа меняет только
  локальный стейт.

**Как чинить:** брать этап из `lead` (с `useEffect` при смене `id`), а
демо-данные использовать только как первичное наполнение, не как fallback.

### 8. Задачи не сохраняются и не видны остальным экранам
`TasksPage` держит `useState(myTasks)`: отметка «выполнено» и новая задача
живут до ухода со страницы. Шапка («Просрочено») и аналитика считают статический
`TASKS`, поэтому цифры расходятся. Новая задача к тому же всегда получает
`leadId: 1`.

**Как чинить:** вынести задачи в тот же провайдер, что лиды, с ключом
`crm.tasks.<id>.v1`, и считать счётчики оттуда.

## P2. Среднее

9. **Поиск в шапке не работает.** `Shell` хранит `query`, но нигде его не
   использует; поиск подключён только на «Клиентах» через пропсы. На воронке,
   заявках, задачах и аналитике поле выглядит живым, но ничего не фильтрует.
   Подсказка `⌘K` не реализована и на Windows бессмысленна.
10. **«+» в колонке создаёт пустую карточку** «Новый лид» с городом «Москва»
    и нулевой суммой (`addLead({ name: "Новый лид", ... })`). На скриншотах
    владельца это выглядит как мусор на доске. Логичнее открывать диалог
    создания с предвыбранным этапом.
11. **Сброс воронки и удаление этапа без подтверждения.** «Сбросить мою
    воронку» одним кликом уничтожает правки пользователя; удаление этапа
    сразу переносит лиды. Отмены нет.
12. **Удаление этапа не перенумеровывает позиции.** Лиды переезжают с
    прежними `position`, две колонки начинают делить номера, порядок прыгает
    до перезагрузки (там его чинит `loadState`).
13. **Дублирующий поиск на «Клиентах»** — в шапке и в тулбаре, оба привязаны
    к одному состоянию. Один из них лишний.
14. **Аналитика не связана с доской.** `myLeads`, воронка и крупные сделки
    считаются из статического `STAGES`: новые лиды, переименованные этапы и
    сброс на цифрах не отражаются. Плюс конверсия и маржа — константы
    (19/24/27% и 26%), а не расчёт.
15. **Мёртвые кнопки.** «Позвонить», «Письмо», «Ещё», «Прикрепить файл»,
    «Создать заявку», «Пригласить», «Добавить», «Создать копию», «Копировать»,
    «Удалить», «Выйти», колокольчик, «Просрочено» — без обработчиков. Для
    витрины допустимо, но стоит либо отключить их видом, либо дать реакцию.
16. **Одинаковые данные у всех лидов.** Файлы, история, теги («Тент»,
    «Постоянный»), бухгалтер «Смирнова О. П.» и текст «Последнее действие»
    захардкожены в `LeadPage` и не зависят от лида.
17. **Новый лид не открывается после создания**, а подсказка «Лид появится на
    первом этапе „Новый“» жёсткая: этап мог быть переименован.
18. **Нет `ErrorBoundary`.** Любая ошибка рендера (например, битые данные в
    `localStorage`) даёт белый экран без объяснения. Для макета, который
    показывают заказчику, лучше экран «что-то сломалось, сбросить данные».
19. **Нет валидации и миграции сохранённых данных.** `JSON.parse` без проверки
    формы: этап без `id`/`name` или лид без `priority`/`contact` роняет
    страницы (`PRIORITY[lead.priority].cls`, `contact.localeCompare`).
    Ключи версионированы (`v1`), но версия нигде не читается и не мигрируется.

## P3. Мелочи и гигиена

20. **Модалка без фокуса.** Нет перевода фокуса внутрь, ловушки, блокировки
    прокрутки фона, возврата фокуса и `aria-labelledby`; заголовок отдаётся
    только `aria-label`.
21. **Строки таблиц кликабельны, но недоступны с клавиатуры.** В «Клиентах»,
    «Заявках» и списке лидов `<tr onClick>` без `tabIndex`/`role`/Enter —
    с клавиатуры карточку не открыть.
22. **Колонки могут схлопнуться на низком окне:** `max-height:
    calc(100vh - 330px)` при высоте окна меньше ~400 px обнуляется.
23. **Отрицательные позиции.** `addLead` ставит `position: top - 1`, при
    повторных добавлениях уходит в −2, −3… Работает, но нормализации не хватает.
24. **Мёртвый код и слабая плотность:** `FUNNEL_KPI` в `data.js` не
    используется; настройка плотности меняет лишь `--row-h` и `--pad-page`,
    поэтому разница между «Просторно» и «Компактно» почти незаметна.
25. **Следы старого названия:** пакет `transline-crm`, `version 0.1.0`,
    почты `@transline.ru` в демо-данных при бренде «Детроид».
26. **Нет линтера, форматтера, тестов и CI.** `package.json` без
    `lint`/`test`/`engines`. Для макета терпимо, но при передаче агенту
    отсутствие автопроверок повышает риск регрессий.
27. **`compact.css` — 731 строка переопределений** поверх 4 000 строк стилей.
    Работает, но это второй источник правды: меняя размер, надо помнить про
    два файла.
28. **`strictPort: true`** в `vite.config.js`: если 5173 занят, dev-сервер
    падает (ловили в песочнице). Удобнее `strictPort: false` или подсказка.
29. **Нет синхронизации между вкладками:** правки в одной вкладке не видны в
    другой, а перезапись при следующем действии затрёт чужие изменения.
30. **Значения из `localStorage` не валидируются по списку** (`crm.theme`,
    `crm.role`, `crm.sidebar`): мусор в ключе даёт «светлую» тему и роль
    менеджера молча — как fallback это нормально, но `data-theme="мусор"`
    останется в DOM.

## Что сделано хорошо

- **Хранилище собрано в одном месте**, обновления иммутабельные, при загрузке
  позиции нормализуются, ключи привязаны к менеджеру.
- **Перетаскивание** продумано: своя `collisionDetection` (карточка важнее
  колонки), линия вставки, слот в пустой колонке, призрак с реальной шириной,
  гашение клика после переноса, клавиатурный сенсор.
- **Бренд** сделан через CSS-маску: один SVG работает в обеих темах и на любом
  размере, без дублирования файлов.
- **Доступность местами аккуратная:** `aria-pressed` у чипов и сегментов,
  `role="switch"` с `aria-checked`, `aria-label` у иконочных кнопок,
  `aria-expanded`/`aria-controls` у сворачивания панели, `prefers-reduced-motion`.
- **Нет XSS-векторов**, `console.log`, `dangerouslySetInnerHTML`; сборка
  компактная, все 11 маршрутов рендерятся серверно без ошибок.
- **Документация** (README, PLAN, PARITY, HANDOVER, STATUS, GAPS,
  MASTER_PROMPT) — редкость для макета и сильно упрощает передачу.

## План правок

Порядок — по риску для доверия к макету. Каждый заход — отдельный коммит,
после каждого `npm run build` и серверный рендер.

**Заход 1. Данные и состояние (P1).**
Пустой массив лидов не подменять демо-данными; вынести применение темы,
акцента и плотности в общий модуль и вызывать до рендера; свести тему к одному
источнику правды; починить KPI «Без движения» и «Потенциальные»; нормализовать
позиции после удаления этапа; не держать этап в локальном состоянии карточки;
не подставлять демо-лид вместо удалённого; задачи — в общий провайдер.
**Оценка:** один заход, 5–7 правок, риск средний (меняются ключи хранения —
нужна аккуратная миграция).

**Заход 2. Поиск и доска.**
Рабочий поиск в шапке (или честно убрать поле), единый поиск на «Клиентах»,
корректная вставка при активном фильтре, «+» в колонке открывает диалог
создания, подтверждения для сброса и удаления этапа.
**Оценка:** один заход, риск низкий.

**Заход 3. Карточка лида и действия.**
Связать аналитику с живыми данными или явно пометить цифры демонстрационными;
одинаковые файлы/историю заменить на данные лида; дать реакцию мёртвым кнопкам
(или убрать их); `ErrorBoundary`; фокус в модалке; клавиатура в таблицах.
**Оценка:** один-два захода, риск низкий.

**Заход 4. Гигиена.**
Линтер и форматтер, `engines`, переименование пакета, валидация сохранённых
данных, `max-height` колонок, синхронизация вкладок, мелкие чистки.
**Оценка:** один заход, риск низкий.

## Как проверять после правок

1. `npm run build` — без предупреждений.
2. Серверный рендер 11 маршрутов (рецепт в `HANDOVER.md`, раздел 11).
3. Ручной чек-лист: удалить все лиды и перезагрузить; сменить акцент и
   перезагрузить другую страницу; сменить тему в настройках и посмотреть на
   иконку в шапке; перетащить карточку с фильтром «Горячие» и снять фильтр;
   открыть один лид, затем другой и сверить этап; создать задачу и уйти со
   страницы; сбросить воронку.
