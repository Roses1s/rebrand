# Перенос визуала в рабочую CRM

Живой документ: как вёрстка этого макета переедет в `Roses1s/crm`
(ветка `arena/3d32f7ee-crm`). Заведён 16.11.2026.

## Кто что делает

- **Этот репозиторий** (`Roses1s/rebrand`) — только макет. Здесь доделывается
  внешний вид всего, что есть в рабочей CRM, и готовятся задания на перенос.
- **Рабочая CRM** (`Roses1s/crm`) — там работает **другой агент**. В её код
  отсюда ничего не пишем. Владелец передаёт тому агенту задания из раздела 6
  этого документа по одному.
- Переносится **именно визуал**: разметка, стили, расположение, состояния.
  Логика, API, права, проверки, тесты и данные рабочей CRM остаются её.

## 1. Решения владельца (16.11.2026)

| Вопрос | Решение |
|---|---|
| Порядок работ | Сначала доделать макет, потом переносить |
| Как включать | Новый вид **рядом со старым**, по переключателю; старый работает, пока владелец не скажет «переключаем» |
| Задачи и Аналитика | В макете остаются; в рабочую CRM — **позже, полноценно**, отдельным проектом с сервером. До этого в новом виде их нет |
| Поля без сервера: оператор ЭДО, срок на карточке, порядок карточек внутри этапа, подсказка этапа | В макете **остаются**; в рабочую CRM — позже, когда сервер научится их хранить |
| Приоритет | **Звёзды 0–3**, как в рабочей CRM: клик по звезде сохраняет, повторный клик по той же снимает |
| Вход | Рисуется в новом стиле — **позже**: вход и авторизацию пока не трогаем |
| Лаунчер | Убирается: после входа сразу открывается воронка |
| Прототип `/crm2` в рабочей CRM | Заменяется новым видом и затем удаляется |

## 2. Почему нельзя «скопировать папку»

| | Макет | Рабочая CRM |
|---|---|---|
| Язык | JavaScript (JSX) | TypeScript, строгие типы |
| Стили | собственные CSS-файлы, токены в `tokens.css` | Tailwind v4, токены `--odoo-*` в `index.css` |
| Данные | `localStorage`, `src/app/store.jsx` | API через react-query (`shared/api/hooks`) |
| Проверки | `npm run build`, SSR-смоук | ESLint, Prettier, `tsc -b`, 66 файлов тестов с порогом покрытия, сборка |
| Сборка | Vite 8 | Vite 6 |

Поэтому каждый компонент переписывается: разметка и классы берутся из
макета, а данные и обработчики — из существующего кода рабочей CRM.

## 4. Что ещё доделать в макете до переноса

Источник — [`../PARITY.md`](../PARITY.md), всё со статусами «план» и «в работе».
Порядок согласован с владельцем:

1. **Доска и карточка лида** — звёзды, теги, ответственный, меню «⋯»,
   сворачивание колонок, доска сотрудника для админа; проигрыш с причиной,
   полоса «Проигран», «Восстановить / Взять себе», передача, удаление,
   «предыдущий / следующий», ошибки и конфликт версий.
2. **Заявки, клиенты, админка** — полная карточка заявки, поиск и
   «Показать ещё» в списках, ошибки с «Повторить», диалоги админки,
   «Безопасность».
3. **Вход и меню профиля** — позже, по отдельному решению владельца.

## 5. Данные, которых в рабочей CRM нет

Видны в макете, но при переносе **не показываются**, пока сервер их не хранит:

- `lead.edo` (оператор ЭДО) — новое поле и справочник;
- `lead.due` / `lead.late` (срок на карточке, «просрочено») — нужна сущность задач;
- `lead.position` (порядок внутри этапа) — поле позиции и эндпойнт перемещения;
- `stage.hint` (подсказка этапа) — новое поле этапа;
- `lead.hot`, KPI «Горячие», «Без движения», чип «Просрочено», план месяца,
  колокольчик — нет источника данных;
- маржа в макете — `сумма клиента − сумма перевозчика`; в рабочей CRM она
  считается сервером с НДС и вычетом 25 % — при переносе берётся серверная.
